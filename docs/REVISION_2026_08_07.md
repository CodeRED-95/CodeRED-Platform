## Problemas Encontrados y Corregidos

### 1. ❌ PROBLEMA: `SQLSTATE[42703]` - Columna No Existe

**Síntoma**:
```
Scheduler error: php artisan tokens:expire-pending-requests
SQLSTATE[42703]: Undefined column: 
column "encrypted_plain_text_token" does not exist
```

**Causa Raíz**:
- La migración `2026_08_02_220630_modify_api_token_requests_for_secure_delivery.php` tenía lógica defectuosa
- Intentaba renombrar `encrypted_plain_text_token` a `token_ciphertext`
- Luego intentaba agregar columnas después de `encrypted_plain_text_token` (que ya no existía)
- El código de la aplicación seguía usando el nombre antiguo de columna
- Resultado: aplicación esperaba una columna que no existía en BD

**Solución Aplicada**:
- ✅ Creada nueva migración `2026_08_07_000001_fix_api_token_requests_schema.php`
- ✅ Corrige el esquema revirtiendo los cambios defectuosos
- ✅ Usa `Schema::hasColumn()` para ser idempotente
- ✅ Elimina seguramente columnas adicionales que fueron agregadas incorrectamente

**Archivo**: `database/migrations/2026_08_07_000001_fix_api_token_requests_schema.php`

### 2. ❌ PROBLEMA: Duplicate Key Constraint en `shalom_delivery_records`

**Síntoma**:
```
PostgreSQL error: duplicate key value violates unique constraint
Key (typname, typnamespace)=(shalom_delivery_records, 2200)
SQLSTATE: current transaction is aborted
```

**Causa Raíz**:
- Múltiples contenedores (app, queue, scheduler) ejecutaban migraciones simultáneamente
- Docker compose inicia los 3 contenedores casi al mismo tiempo
- Cada uno ejecutaba `php artisan migrate --force` desde el entrypoint
- Resultado: race condition intentando crear la misma tabla

**Solución Aplicada**:
- ✅ Removidas migraciones automáticas del `docker/php/entrypoint.sh`
- ✅ Ahora las migraciones se ejecutan SOLO desde `update.sh` (paso 7)
- ✅ Migraciones de tablas hechas idempotentes con `Schema::createIfNotExists()`
  - `2026_08_06_000002_create_shalom_delivery_records_table.php`
  - `2026_08_06_000003_create_shalom_api_keys_table.php`
  - `2026_08_06_000005_create_ruc_backups_table.php`

**Archivos Modificados**:
- `docker/php/entrypoint.sh` - Removidas líneas 46-47
- Migraciones Shalom y RUC - Cambiadas a `createIfNotExists()`

### 3. ❌ PROBLEMA: PHP-FPM Workers Reciben SIGKILL

**Síntoma**:
```
PHP-FPM logs: child XX exited on signal 9 (SIGKILL)
Múltiples workers nuevos muriendo después de 7-14 segundos
```

**Causa Raíz**:
- Las migraciones automáticas del entrypoint estaban causando race conditions
- Esto generaba bloqueos y deadlocks en PostgreSQL
- PHP-FPM parecía no responder
- Nginx presumiblemente pudo haber matado workers o Docker reiniciar contenedores

**Solución Aplicada**:
- ✅ Removidas migraciones automáticas (ver problema #2)
- ✅ Agregados timeouts apropiados en Nginx para PHP-FPM
  - `fastcgi_connect_timeout: 60s`
  - `fastcgi_send_timeout: 300s`
  - `fastcgi_read_timeout: 300s`
- ✅ Aumentados tamaños de buffer para respuestas grandes

**Archivos Modificados**:
- `docker/nginx/default.conf` - Agregados timeouts en ubicación PHP

### 4. ❌ PROBLEMA: Agent Recibe JSON Parsing Error Confuso

**Síntoma**:
```
Agent logs: Unexpected token '<', "<!DOCTYPE "... is not valid JSON
```

**Causa Raíz**:
- Cuando PHP-FPM estaba caído, Nginx devolvía 502 Bad Gateway con HTML de error
- El cliente HTTP del agente intentaba parsear el HTML como JSON
- `JSON.parse()` fallaba con mensaje confuso
- No quedaba claro que el problema era 502, parecía un problema de parsing

**Solución Aplicada**:
- ✅ Mejorado `CodeREDClient.ts` para capturar errores de JSON.parse() separadamente
- ✅ Verifica `Content-Type` de la respuesta
- ✅ Crea un `HttpError` apropiado que incluye:
  - El status HTTP (502/504)
  - El Content-Type recibido
  - Una muestra pequeña de la respuesta (primeros 200 chars)
- ✅ Logs ahora claros: "CodeRED request failed 502: text/html"

**Archivo Modificado**:
- `packages/codered-agent/src/protocol/CodeREDClient.ts` - Métodos `bearer()` y `raw()`

### 5. ❌ PROBLEMA: Sin Scheduler Configurado

**Síntoma**:
```
No hay registro formal de comandos programados
php artisan schedule:list no muestra comandos de CodeRED
```

**Causa Raíz**:
- No existía un `app/Console/Kernel.php`
- Laravel usaba default que no tenía comandos programados

**Solución Aplicada**:
- ✅ Creado `app/Console/Kernel.php` que registra:
  - `ExpirePendingTokenRequestsCommand` ejecutado cada hora
  - Usa `onOneServer()` para evitar ejecuciones duplicadas si hay múltiples schedulers
- ✅ Ahora `php artisan schedule:list` muestra los comandos esperados

**Archivo Creado**:
- `app/Console/Kernel.php`
